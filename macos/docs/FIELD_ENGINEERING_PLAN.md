## 开发顺序与完成条件

本页统一维护现场产品顺序；T01–T16 工程依赖及整项验收仍以任务清单为准。每一步按本切片所需能力设门槛，T15 的实机与发布取证贯穿各步。

### 1 · P0 · 验收中文交接单与基线回看

**当前切片：已有实现，先收口验收。** 后续工程师应能在离线项目中找对交接版本，并查清当初的业务判据和已知例外。使用人工记录及既有诊断快照，不以联网诊断和 T04 分页为前置门槛；这两项可并行推进。

1. **建模与兼容。** 复用 `NMCore/FieldProject` 和 `NMAssets/FieldProjectDocument`。为现场需求、PoC 或验收项目、测点和交接版本建立稳定引用。记录方案版本、目标或点位、观测条件、判据及单位、证据来源、责任人。判定支持待测、受阻、通过、不通过，另存经确认的例外及确认人、日期和复测安排。缺判据、缺证据或变更后未复核的项保留待确认语义。区分工程师填写、客户材料、历史快照与本次实测。用 `NMTest` 验证 v1 打开、保留旧字段和证据、升级保存后重开，以及文件损坏或超限时的提示。既有字段从读取到版本生成均通过模型操作，SwiftUI 复用其结果。
2. **版本与复核。** 由工程师确认生成交接版本，保存当时的判据、状态、例外及证据副本。后续修改草稿时原版本在应用内只读，售后草稿通过版本 ID 回看。试点支持同站点查看两个版本并明确选择，PoC 通过只在该 PoC 记录生效。客户对正式验收以其签批为准，项目文件可由外部编辑，版本的只读约束由应用提供。先用有明确上限的版本快照验证文档大小，并在保存前提示空间不足。
3. **交接导出。** 沿用原生打开、保存和预览流程。默认摘要只包含允许分享的检查状态与证据计数。详细交接由用户逐项选入字段，预览内容与导出文本一致。把客户名、内网地址、SSID/BSSID、序列号、凭据和自由文本中的测试标记纳入导出检查。客户交接所需的判据、未测原因和跟进责任由工程师复核后选入。中文验收单与现有本地化一并检查。
4. **整条离线验收。** 用虚构办公园区的无线更新项目，建 3 条需求、2 个测点以及至少 1 个未测项、1 个受阻项和 1 个确认例外。保存第一个交接版本，修改方案后再生成一版，重开项目并从售后草稿准确定位旧版。用隔离数据在 Release arm64 `.app` 的中文界面验证 v1 重开、损坏或超限提示、键盘可达、v2 选版及旧判据不变；确认默认和逐项选入两种报告的预览与落盘一致，默认文件名不含客户值。由另一名工程师仅凭分享版核对已选结论、观测条件、未结事项和跟进人。此场景使用合成资料和已有快照。

### 2 · P0 · 授权单服务复测与割接核验

把已交接基线用于受控复测。从验收项带入已知目标，工程师复核授权引用、时间窗、单一目标与方法后显式启动。维护事件可将其固定的交接版本和设备地址带入复测表单；工程师仍需选择交接测点与方法、填写当前网络条件并重新确认授权。选中基线行或证据不会覆盖事件设备地址。完成结果先由工程师显式附加到项目，再单独关联到事件时间线；准备复测及完成探测本身均不改写事件记录。先做系统 DNS 与 TCP 纵切，指定 DNS 或已知 IP 只作为用户单独发起的对照；TLS 信任和 HTTP HEAD 响应现已分别接入，未经单独测试的层不报成功或失败；本批本机验证与限制见[TLS/HTTP 实施记录](T06_TLS_HTTP_2026-11-19.md)。复用 `DiagnosticService` 和 T01–T03 的类型化错误、总时限和取消机制。记录时间、实际对端、地址族、DNS 模式及可观测路径；区分系统快照、实际连接和人工补记。换网后记录独立观测，关键条件变化或缺失时标为“不可直接比较”；旧结果及交接版本不变，只有工程师选中的证据才写入项目。限定前台、单服务和本地保存。

## 试点如何验收产品价值

拟从集成商售前、交付和驻场售后各邀请参与者，合计 5–8 人。在三个脱敏样例上记录现有流程与新版表现，样例覆盖方案变更、带例外交付和故障复测。优先用虚构项目做第一轮，后续现场数据由客户明确授权使用。以下阈值为试点目标，统计取自现场任务观察和导出检查表。

| 指标 | 计算与判据 |
|---|---|
| 必检项可复核率 | 由试点清单标记必检项。能核对测点、判据和条件，且有证据或明确受阻原因的必检项 ÷ 必检项总数。单纯待测不计可复核，受阻也不计通过。受控样例目标 100%，另记追问次数。 |
| 正确找到交接基线 | 从打开售后草稿到找到对应版本和观测条件，记录耗时中位数和选错次数。先确认三个任务的版本关联正确，再据现有流程实测设耗时目标。 |
| 对外报告可分享性 | 逐份复核默认摘要和挑选字段后的导出。标记的客户敏感值不得出现在未选字段、默认文件名或导出文本中。报告保留的必要业务信息由接收人确认，预览与落盘一致。 |
| 复测状态准确性 | 按上述受控复测用例检查状态及不可比提示，整组预期匹配后才算通过该切片。另记权限拒绝后的恢复步骤及所需时间。 |

## 当前版本怎么用

1. 在主窗口进入「现场工程 → 现场项目」，选择「新建现场项目」。填写客户、站点和项目范围。
2. 切换售前、交付和售后面板，为结论填写判据和证据。记录业务性能基线后，在售后面板回看。
3. 在具体检查项选择「附加诊断」，选择已结束的历史记录，按需补录当时的网络条件，再附加并用 `⌘S` 保存。移除附件只影响该检查项。
4. 普通检查表用「预览报告」：默认只显示检查结论和关联数量，详细选项会输出项目文本、诊断快照及人工巡检字段。结构化验收使用单独的验收报告：先选草稿或交接版本，再逐行选择需要分享的字段。
5. 在「售后维护 → 维护事件」新建事件，选择可选交接版本和设备快照，记录负责人和外部工单号；添加报障、响应、恢复或复测时间线，按需显式关联同版本已保存复测。最后用 `⌘S` 保存。NetBox 预览中的已有设备可手动选择刷新。
6. 在「现场项目 → 检索项目事件」显式选择项目文件，按文本、状态、发生时间或设备查找已保存事件；查看来源和时间线，按需打开源项目。保存源项目的改动后，使用「刷新已载入文件」更新本次检索。
7. 在「现场项目 → 本地事件库」选择「导入项目快照」，保存已选文件的本机副本；关闭重开后继续查询。展开来源列表可刷新快照或移除本地副本，源项目文件会保留。
8. 在 NetBox 设备预览行选择「读取接口与地址」，成功后确认新增或刷新，才将来源清单保存到资产。在资产详情的「配置接口与地址」查看双栈、VRF 和独立读取时间；该来源快照不代表 Mac 的实际路由或可达性。
9. 在售后维护的「人工巡检」中创建模板，为每项填写名称、目标和判据；选择模板开始巡检，填写负责人、逐项结果与证据，并记录整改负责人和期限。保存项目后可重开记录；编辑模板只影响之后创建的记录。巡检由人工填写，不会启动网络探测。普通报告默认不包含这些录入字段，详细报告包含经凭据脱敏的巡检内容。
10. 在「维护事件」详情选择「准备复测」后，确认带入的事件交接版本和设备地址，选择交接测点、复测方法并填写当前网络条件。填写变更单、批准人和窗口，再勾选授权确认并点击「开始复测」；只有此操作会启动单服务诊断。先显式附加完成结果，再回到事件时间线新增记录并选择该已保存结果。准备表单不会沿用旧授权或网络条件，也不会自动写入事件时间线。

现有项目文件以明文 JSON 保存客户资料、诊断目标与工程记录。已知凭据形式在生成诊断快照时脱敏，内部地址、主机名及自由文本仍可能属于客户敏感信息。选择客户批准的本地存储与传递方式。源文件中的证据副本由工程师在项目内管理，详细导出选项只影响报告。 [诊断证据导出](../Sources/NMCore/DiagnosticEvidence.swift)
